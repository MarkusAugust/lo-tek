# LO-TEK in Kotlin and Java

The rulebook for LO-TEK on a JVM server: Ktor, Spring, Javalin, http4k or
anything else that writes HTML from Kotlin or Java, with kotlinx.html, in
strings, or with a template engine such as JTE, Thymeleaf, Freemarker or
Pebble.

Nothing here needs Node or npm. The Maven package has the builder functions as
`Lt`, with enums for the allowed values, the check as `assertLotek(html)` for
your tests, and the CSS and the web components as a WebJar the app serves
itself.

The compiler is the first check: `ButtonVariant.SECUNDARY` does not compile,
so code that calls the builder functions cannot invent a variant. It does not
see markup written by hand next to them, or the wiring across a whole page.
That is what `assertLotek` reads.

This is @lo-tek/interfaces 0.40.0. The file is generated by the package and
follows its version, so it can never say anything other than the code next to
it.

## Short version

1. **One `<link>` to `LotekWebJar.CSS` in the page template,** once for the
   whole app, with the WebJar served under `/webjars`. Without it, the
   components look unstyled. The answer is then to add the link, never to
   write your own CSS to make them look right.
2. **Use only the classes and elements in the tables below.** `lt-modal`,
   `lt-datepicker` and `data-variant="outlined"` exist in other design
   systems, not in LO-TEK. If you are unsure whether something exists, it is
   listed here or it does not exist.
3. **No hard-coded colours or pixels.** `var(--lt-color-…)` and
   `var(--lt-spacing-…)`.
4. **Web components are registered once with `defineLt()` from
   `LotekWebJar.REGISTER`** in the page template, and a boolean attribute is
   true as long as it is there. In kotlinx.html a flag property set to `false`
   removes the attribute, while `attributes["hidden"] = "false"` still hides
   the element.
5. **Check the HTML the server sends, in a test:** `assertLotek(html)` fails
   with every finding as `line:column: error: message`, or `warning:`. It
   knows every class, every element, every attribute and every allowed value,
   and on a whole page it also requires every `for` and `aria-describedby` to
   point to an id that exists, and every field to have a label. With the app
   running, also check every page you have changed:
   `java -jar lotek.jar check http://localhost:8080/page`. You are done when
   the tests are green and the command answers "The markup matches LO-TEK".

## 1. The package, the stylesheet and the registration

```kotlin
// build.gradle.kts
dependencies {
    implementation("io.github.markusaugust:lo-tek-interfaces:0.40.0")
    // Only with kotlinx.html: the extension lt(…) and one function per web component.
    implementation("io.github.markusaugust:lo-tek-kotlinx-html:0.40.0")
}
```

The version is the npm package's, but not every npm version is on Maven
Central. Use the newest one there, and never write a version you have not seen
on
https://central.sonatype.com/artifact/io.github.markusaugust/lo-tek-interfaces.
The package requires Java 17 or newer.

The package is also a WebJar: the files are under
`META-INF/resources/webjars/lo-tek/<version>/`, with the same paths as in the
npm package. Spring Boot and servlet containers serve that folder without
setup. Ktor needs one line in `routing`:
`staticResources("/webjars", "META-INF/resources/webjars")`.

`LotekWebJar` has the paths with the version in them, so the page never points
to a version other than the one the package has. The page template, once for
the whole app:

```kotlin
head {
    link(rel = "stylesheet", href = LotekWebJar.CSS)
}
body {
    // The page.
    script(type = "module") { unsafe { +"import { defineLt } from \"${LotekWebJar.REGISTER}\"; defineLt()" } }
}
```

The same in a string, without kotlinx.html:

```kotlin
fun page(content: String) = """
<!DOCTYPE html>
<html lang="en">
<head><link rel="stylesheet" href="${LotekWebJar.CSS}"></head>
<body>
$content
<script type="module">
  import { defineLt } from "${LotekWebJar.REGISTER}"
  defineLt()
</script>
</body>
</html>
"""
```

`lotek.css` is 112 kB, 14 kB compressed, has every component, and is nearly
always the right choice. If you want only the stylesheets the pages use,
`tokens.css` defines all the variables, and all the other stylesheets build on
it. It must be loaded, and comes first out of habit: the order between it and
the others does not matter. After that, one stylesheet per component, from the
tables below, each under `LotekWebJar.ROOT`.

## 3. Tokens

One layer. A colour is a cell in a matrix of **family**, that is, what it
means, and **role**, that is, what it does, and the name is
`--lt-color-<family>-<role>`. Every family has every role, so
`--lt-color-danger-border` and `--lt-color-success-border` both exist. The
roles are the same whatever the family: `surface` is a tinted surface, `fill`
a filled one, `content` the text on top of `fill`, `border` a border, and
`text` the family's colour as text. Border and text each have a weaker and a
stronger step next to them.

```
Families: `accent`, `visited`, `brand1`, `brand2`, `brand3`, `neutral`, `danger`, `warning`, `success`.

Roles: `surface`, `border-subtle`, `border`, `border-strong`, `fill`, `text`, `text-strong`, `text-subtle`, `content`.

Outside the matrix: `--lt-color-disabled-surface`, `--lt-color-disabled-text`, `--lt-color-neutral-canvas`, `--lt-color-neutral-raised`, `--lt-color-overlay`, `--lt-focus-ring`, `--lt-icon-calendar`, `--lt-icon-check`, `--lt-icon-clock`, `--lt-icon-dash`, `--lt-icon-search`, `--lt-shadow-overlay`.
```

Spacing: `--lt-spacing-0-5`, `--lt-spacing-1`, `--lt-spacing-10`,
`--lt-spacing-12`, `--lt-spacing-16`, `--lt-spacing-2`, `--lt-spacing-3`,
`--lt-spacing-4`, `--lt-spacing-5`, `--lt-spacing-6`, `--lt-spacing-7`,
`--lt-spacing-8`, `--lt-spacing-px`.

Font: `--lt-font-size-l`, `--lt-font-size-m`, `--lt-font-size-mega`,
`--lt-font-size-reference`, `--lt-font-size-s`, `--lt-font-size-xl`,
`--lt-font-size-xs`, `--lt-font-size-xxl`, `--lt-font-size-xxs`,
`--lt-font-weight-bold`, `--lt-font-weight-medium`,
`--lt-font-weight-regular`, `--lt-font-weight-semibold`.

Line height: `--lt-line-height-article`, `--lt-line-height-compact`,
`--lt-line-height-default`, `--lt-line-height-heading`.

`disabled` and `neutral` are not the same. `disabled` is for controls that are
turned off, and is exempt from the contrast requirement in WCAG 1.4.3.
`neutral` is for subdued information the user actually has to read or press,
and holds 4.5:1. Never use the `disabled` colours to subdue something that is
meant to be read.

### Light and dark

Without you doing anything, the colours follow the device's setting. A page
that wants to decide for itself sets `data-theme="light"` or
`data-theme="dark"` on `<html>`.

The attribute is a **theme boundary** and works on any element, not only on
the root. One theme can sit inside another, both ways.

This is what an embedded component should use. When you put LO-TEK into a page
you do not control, set the attribute on the component's own root element:

```kotlin
div {
    attributes["data-theme"] = "light"
    button { lt(Lt.button()); +"Save" }
}
```

The component is then light whatever the device is set to, and the host is
left alone.

**The host's CSS stops at the boundary.** The host often has rules without a
layer, such as `button { background: none; border: none }` or a normalize, and
they beat `@layer lotek`. In that case, set `data-lt-boundary` on the same
root element:

```kotlin
div {
    attributes["data-lt-boundary"] = ""
    attributes["data-theme"] = "light"
    button { lt(Lt.button()); +"Save" }
}
```

Below the root element the browser then ignores the host's CSS without a
layer, unless a rule of the host's wins on specificity as described below, and
LO-TEK's layer applies again. The rule is in `lotek.css` and in
`${LotekWebJar.ROOT}/src/tokens/boundary.css`. Fonts and other inherited
properties still come from the host, and the `--lt-*` variables work. Three
things follow from it:

- Your own CSS inside the boundary must be in a layer after `lotek`. CSS
  without a layer disappears there in the same way as the host's.
- Elements without a LO-TEK class lose the host's CSS without a layer. A layer
  the host has declared before `lotek`, such as Tailwind's Preflight in
  `base`, still applies where LO-TEK sets nothing.
- The boundary has the specificity (0,2,0). A rule from the host with the same
  specificity wins if it is loaded after the boundary, and one with more
  always wins. So do `!important` and layers the host has declared after
  `lotek`.

LO-TEK sets `color-scheme` only where someone has chosen a theme: on
`[data-theme="light"]`, on `[data-theme="dark"]` and on the options of the
theme picker below. Bare `:root` never gets it. The property controls the
browser's own surfaces, that is, scrollbars, dropdowns and calendar panels,
and it is inherited. A child can opt out with `color-scheme: normal`, but that
is a counter-rule the host never asked to have to write: with the value on the
root, it applied to the whole document, including where the package is only a
guest. If the whole page should follow the system, write
`color-scheme: light dark` on `<html>` yourself, in the same way as you set
the layer order yourself.

### Letting the user choose a theme

`lt-theme-control` on a radio button makes `value` a theme choice. It is plain
CSS, without a line of JavaScript:

```kotlin
fieldSet {
    lt(Lt.toggleGroup())
    legend { lt(Lt.srOnly()); +"Theme" }
    label {
        lt(Lt.toggleGroup.option)
        radioInput(name = "theme", classes = "lt-theme-control") { value = "auto"; checked = true }
        +" Follow the system"
    }
    label {
        lt(Lt.toggleGroup.option)
        radioInput(name = "theme", classes = "lt-theme-control") { value = "light" }
        +" Light"
    }
    label {
        lt(Lt.toggleGroup.option)
        radioInput(name = "theme", classes = "lt-theme-control") { value = "dark" }
        +" Dark"
    }
}
```

`lt-theme-control` has no builder function, so it is the one class written as
a string.

The choice controls two things. LO-TEK's colours come from the tokens, and the
browser's **own** surfaces from `color-scheme`: `light` gives `light`, `dark`
gives `dark`, and `auto` gives `light dark`. `light dark` is not a theme, but
the statement that the page works in both, so the browser can choose by the
system.

"Follow the system" has no theme block, and that is on purpose: a value
without a block matches nothing, and then the media query applies again.

Do not write `color-scheme` yourself when the picker is in use. Such a rule
outside a layer beats `@layer lotek` and locks the browser's surfaces to the
system while the user has chosen something else.

`light` and `dark` win over `data-theme` on `<html>`, so the server can send
the stored choice while a click still takes effect before the response is
back. `auto` does not: it means "no override from me", so if the server has
written `data-theme`, the server's value stands. For "follow the system" to
work at once, whatever stores the choice must also remove the attribute.

Two things it does not do. It **stores nothing**: submit the group in a form
and store the choice in a cookie the server reads, or in `localStorage`. And
it must be in the **same tree as `<html>`**, since `:has()` does not see out
of its own tree; a control inside a shadow root does not set the theme on the
page.

## 4. Web components

Three rules apply to all of them:

1. **`defineLt()` runs once** in the page template, not once per component.
   The import has no side effect on its own; it is the `define` call that
   registers the element.
2. **Boolean attributes are true as long as they are present.**
   `hidden="false"`, `disabled="false"` and `open="false"` turn it *on*. To
   turn any of them off, remove the attribute entirely.
3. **You write the markup, the component adds the behaviour.** `<lt-field>`
   does not create your label or your control. With `Lt.field()` the server
   writes the whole wiring, and `<lt-field>` is not needed; it is for markup
   that cannot call a builder function, such as a JTE template. There you
   write `for` on the label and `id` on the control, or wrap the control in a
   `<label>`, and the component wires the help text and the error text. It
   never writes an id on the control: an id the server did not send makes an
   update from the server replace the field, with the focus and what the user
   has typed. The field is invalid when the error text is there without
   `hidden`.

## 5. The builder functions

`Lt` has the same builder functions and options as `lt` in TypeScript. Each
gives the attributes for one element, as an `Attributes`, which is a
`Map<String, String>`. In kotlinx.html, `lt(…)` puts them on the tag; in a
string, `toHtml()` writes them out with the values escaped, and `+` combines
two sets:

```kotlin
val save = Lt.button(variant = ButtonVariant.SECONDARY)

button { lt(save); +"Save draft" }

val asText = """<button ${save.toHtml()}>Save draft</button>"""
```

Both give
`<button class="lt-button" data-variant="secondary">Save draft</button>`. In
kotlinx.html several sets are applied in order, a later one wins, and the
classes are added to those the tag already has.

`Lt.errorText()`, `Lt.field()`, `Lt.fieldset()`, `Lt.fileUpload()`,
`Lt.heading()`, `Lt.helpText()`, `Lt.icon()`, `Lt.input()`, `Lt.label()`,
`Lt.legend()`, `Lt.link()`, `Lt.list()`, `Lt.pagination()`, `Lt.paragraph()`,

Every enum has `value`, the text in the HTML, and `of(text)`, which gives the
constant, or `null` for a text that is not allowed. A value from a request
goes through `of` with a fallback:
`ButtonVariant.of(text) ?: ButtonVariant.PRIMARY`, never `!!`, which throws
without saying what the text was.

kotlinx.html has an `InputType` of its own. Import `no.lotek.InputType` by
name next to `kotlinx.html.*`, as the recipes do, and use kotlinx.html's
shortcuts, such as `radioInput`, for its own types.

From Java the builder functions are static methods on `Lt`, and options can be
left out from the end:

```java
Attributes save = Lt.button(ButtonVariant.SECONDARY);
```

## 6. A field

`Lt.field()` writes the whole wiring between the label, the control, the help
text and the error text, every time the server renders the form. The field
then needs no `<lt-field>` and no script: `<lt-field>` is for markup that
cannot call a builder function, such as a JTE template. Never use both on one
field. This is the recipe from the field page, compiled and compared with its
HTML on every build:

```kotlin
import kotlinx.html.*
import no.lotek.*
import no.lotek.InputType
import no.lotek.html.lt

fun FlowContent.orderForm(codename: String = "", invalid: Boolean = false) {
    val field = Lt.field(id = "codename", required = RequiredMarker.SYMBOL, error = true, invalid = invalid)
    form(action = "/jobs", method = FormMethod.post) {
        id = "order-form"
        attributes["novalidate"] = ""
        label { lt(field.label); +"Codename" }
        input {
            lt(Lt.input(type = InputType.TEXT), field.control)
            name = "codename"
            required = true
            // What the user typed comes back, so a failed submission loses nothing.
            if (codename.isNotEmpty()) value = codename
            if (invalid) autoFocus = true
        }
        p { lt(Lt.errorText(), field.error); +"Enter a codename." }
        button { lt(Lt.button()); type = ButtonType.submit; +"Order the job" }
    }
}
```

The page template around it:

```kotlin
// Once for the whole app, in the page template. Not once per component.
head { link(rel = "stylesheet", href = LotekWebJar.CSS) }
body {
    orderForm()
    script(type = "module") { unsafe { +"import { defineLt } from \"${LotekWebJar.REGISTER}\"; defineLt()" } }
}
```

The handler for `POST` renders the form again with what was typed and
`invalid = true`, with status 422, and the error text shows. A valid
submission redirects, so a reload does not post it again.

**The id is required, and an empty one throws.** Make it from a key in the
data, never from the loop index, a counter or a random value, so it is unique
on the page and the same on every render:

```kotlin
data class JobNote(val code: String, val name: String, val text: String)

fun FlowContent.notes(jobs: List<JobNote>) {
    for (job in jobs) {
        val field = Lt.field(id = "note-${job.code}")
        label { lt(field.label); +job.name }
        input { lt(Lt.input(), field.control); name = "note-${job.code}"; value = job.text }
    }
}
```

A morph, as in Datastar or htmx with idiomorph, recognises an element by its
id, and replaces one whose id changed, along with the focus and what the user
had typed. With the index the element is kept, but the text ends up in the
wrong row.

## 7. When the server sends new HTML

If the page is patched as it runs, with Datastar, htmx or Turbo, the web
components put back what the user chose when a patch tears it away: the
selected tab in `<lt-tabs>`, an open `<lt-popover>`. The server needs nothing
for that. If the server is to move the state, as in "go on to step 2", write
`server-controlled` on the host. Then every patch decides, and the component
stops putting the user's choice back. The state is always in the markup the
server sends: `aria-selected` on the tab and `hidden` on the panel in
`<lt-tabs>`, and `open` on `<lt-popover>` and `<lt-dialog>`.

A `$` that is meant for the page, as in a Datastar expression, is read by
Kotlin as a template. Write `${'$'}count`, or use a `$$"""…"""` string, where
only `$$` interpolates.

## 8. The check

`assertLotek` checks the HTML the server sends, and throws an `AssertionError`
with the findings, which JUnit, Kotest and TestNG all report:

```kotlin
import kotlinx.html.div
import kotlinx.html.stream.createHTML
import no.lotek.assertLotek
import org.junit.jupiter.api.Test

class OrderPageTest {
    @Test
    fun `the order form is correct markup`() {
        assertLotek(page(createHTML().div { orderForm(invalid = true) }))
    }

    @Test
    fun `every note is wired`() {
        assertLotek(page(createHTML().div { notes(listOf(JobNote("222-0481", "Orison", ""))) }))
    }
}
```

By default it checks a whole page: that every id that is pointed to exists,
and that every field is wired. `assertLotek(html, fragment = true)` checks a
piece of a page, such as one component, against the vocabulary only.
`Lotek.diagnosePage(html)` gives the findings as a list instead.
`assertLotekRendered { script -> page.evaluate(script) }` checks the page as a
browser has rendered it, with Playwright for Java, and also fails on a class
no stylesheet styles.

It reads the HTML that comes out, not the code that made it, so it works the
same for strings, kotlinx.html, JTE, Thymeleaf, Freemarker and Pebble: render
the template to a text in a test, and give it to `assertLotek`. In the
template files themselves, write the markup as the component pages show it.
The rulebook for template syntax is
https://lo-tek.sobernetics.no/agent/templates.md.

The Gradle plugin checks the template files as part of `check`, without a test
that renders them. `templates` takes a whole folder, with its subfolders:
`src/main/jte` for JTE, `src/main/resources/templates` for Thymeleaf,
Freemarker and Pebble.

```kotlin
// build.gradle.kts
plugins {
    id("io.github.markusaugust.lo-tek") version "0.40.0"
}

lotek {
    templates.from(fileTree("src/main/jte"))
}
```

`lotek.jar` is the command line, attached to every release on GitHub:
https://github.com/MarkusAugust/lo-tek/releases/latest. It takes an address,
or the template files by name, never a folder:

```bash
java -jar lotek.jar check http://localhost:8080/form
java -jar lotek.jar check src/main/jte/order.kte src/main/jte/jobs.kte
```

A finding you want to keep is suppressed with a comment above the tag:

```html
<!-- lotek-ignore-next unknown-class -->
<div class="lt-experiment">Testing a new layout</div>
```

In IntelliJ the plugin "LO-TEK Interfaces" from JetBrains Marketplace runs the
same check while you type, also in HTML in a Kotlin string marked with
`@Language("HTML")` or `// language=HTML`. In Kotlin it warns about a set on
an element its part cannot be, such as `label { lt(field.control) }`, about
`of(…)!!`, and about an id from the loop index.

## Known pitfalls

| Symptom | Cause |
| --- | --- |
| The styles are missing | The `<link>` to `LotekWebJar.CSS` is missing, or `/webjars` is not served and it answers 404 |
| An `<lt-toast>` or `<lt-connection-status>` shows nothing, an `<lt-session-timeout>` never warns, or another component does nothing | The `define` function has not run. `<lt-toast>` and `<lt-connection-status>` create their content themselves and are empty without it, and `<lt-session-timeout>` does not count the time. The markup in the others comes from you and is there regardless, with two exceptions until they are registered. `<lt-tabs>` shows one panel: of those the server left without `hidden`, the one the URL points to, otherwise the first, and under `server-controlled` always the first. `<lt-suggestion>` hides the list |
| A component speaks English on a page in another language | The text in the markup comes from you, and is written with the app's own translation setup. The few default texts the package has are replaced with `label` and `close-label` on `<lt-toast>`, `offline-text` and `online-text` on `<lt-connection-status>`, `count-none`, `count-one` and `count-other` on `<lt-suggestion>`, and `--lt-label-required-text`, `--lt-label-optional-text` and `--lt-label-required-symbol` in CSS. Numbers and durations follow the nearest `lang`, usually the one on `<html>`. See https://lo-tek.sobernetics.no/translation/ |
| The error text never shows, and the field counts as valid | `attributes["hidden"] = "false"` on the error text, which hides it all the same. Leave the attribute out, or let `Lt.field(invalid = …)` decide |
| `Type mismatch` on `InputType` | kotlinx.html has an `InputType` too. Import `no.lotek.InputType` by name |
| A field loses what the user typed after an update from the server | The id comes from the loop index, a counter or a random value, and changed between two renders |
| `Unresolved reference` or the wrong value in a Datastar attribute | Kotlin read the `$` as a template. Write `${'$'}` |
