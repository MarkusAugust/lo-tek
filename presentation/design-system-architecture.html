Design system architecture

Architecture for a design system without a framework

A text field with a label, help text and an error message is HTML and ARIA. In a design system built for one framework, it is still tied to a framework you cannot replace, and has to be rewritten every time the framework changes direction.

These are five requirements a design system must meet to avoid that, and two it should meet. For each of them: what it involves and what it costs. None of them is free.

The idea fits in one sentence. Making it hold takes the rest of this presentation.

Markup comes from whoever renders it. The web component adds the behaviour.

LO-TEK is the proof that it can be done, not the subject: a design system built to these requirements, published at lo-tek.sobernetics.no and on npm as @lo-tek/interfaces.

Why this is not trivial

The premise: apps in several frameworks, some servers that do not run JavaScript, and a design system that should outlive the apps around it. Where everything is React and will stay React, a React-based design system is a reasonable choice, and this is not for it.

A design system for one framework has one caller. This one has all of these at once:

What happensWhat it takes
React renders a list again and replaces a nodeWhat the web component set on the old node has to be written again
A server sends the HTML again, and every attribute it did not send is removed, with no errorThe same, and the web component can add no nodes of its own
The markup comes from a Go template that cannot call a functionThe wiring between label, field and messages (id, for, aria-describedby) is worked out in the browser, from the same source as everywhere else
A module is imported on a server that has no DOMNothing may touch HTMLElement when it is imported
One browser engine does not have a feature yetThat engine has to give something that works anyway
The consumer writes a CSS rule of their ownIt has to win, without !important

Each row can be met alone. The work is that all of them hold at the same time, in the same component.

Five requirements and two recommendations

Without the first five, a design system breaks somewhere or has to be worked around. Without the last two it works, but it is harder to use and harder to leave.

Requirement 1 of 5 · The browser must be the platform

The apps will be replaced, and the design system is meant to remain

The reason not to build on React is not that something else is better today. It is that a design system outlives the apps around it.

  • Lifetimes differ. React has gone from classes via hooks to server components in ten years. Class components still run, but each shift was work for every library built on React: new APIs to support, or being left behind. A CSS class from ten years ago needed none of it, and neither did a web component written to Custom Elements v1.
  • It only goes one way. From components built on the platform, anyone can make a React package later. A React component can be wrapped as a custom element, but it brings React with it and shows nothing until JavaScript has run, so it never reaches a page that is only HTML from a server.
  • The portfolio spans many frameworks at once. New apps in React, ten-year-old apps in something else, and publishing systems that only send HTML. A design system tied to one framework reaches only the part that uses it.

Design system teamHas to make the independence invisible day to day, or it feels like a step backwards compared with a React library.

ConsumersReact developers do not get ready-made React components, but classes and attributes with types.

Requirement 1 of 5 · The browser must be the platform

The browser already does focus, layers and forms

Most of what is hard in a design system is already solved in the browser. If the design system builds on the browser, that is code nobody has to maintain.

What the browser takes care of

  • The focus trap in a dialog. showModal() makes the rest of the page inert, keeps focus inside and closes with Escape.
  • The top layer. A modal dialog and a popover sit above everything else without anyone counting z-index.
  • The form. Validation, submission and :invalid exist and work without a single line from the design system.
  • Appearance. Colour, shape and spacing are CSS, and are in place before any script has had time to run.

What remains is the part the browser does not do: the wiring between the elements, keyboard handling where the browser has no ready-made control, and a consistent look.

Design system teamHas to follow what each engine ships, and take its own code out when the browser takes the job over.

Requirement 2 of 5 · Markup must come from whoever renders it

Three ways to render, and all of them render again

A design system has to work wherever the markup is rendered. There are three cases.

CSR

The framework in the browser renders from JSON. When the data changes, React re-renders the results, and it can replace a node with a new one.

const response = await fetch("/api/results")
setResults(await response.json())
SSR

The server renders HTML. When something changes it sends the HTML again, and a library such as Datastar merges it into the page. That is called DOM morphing, and it removes the attributes that were not in what the server sent.

Both

The server renders first, React takes over the same nodes in the browser, which is called hydration, and then React renders there. The markup has to be the same in both places: React warns of a hydration mismatch in development, and does not promise to fix it.

In all three, someone other than the web component renders the DOM again. The rest of the presentation calls that a re-render, whichever of the three it is.

Design system teamHas to test every component under all three, and not only under the one it uses itself.

In LO-TEK<lt-suggestion> reads the highlighted option from aria-selected and the number of matches from the list, so it also works when React re-renders the matches after an asynchronous search.

Requirement 2 of 5 · Markup must come from whoever renders it

DOM morphing removes every attribute the server did not send

SSR with DOM morphing is the strictest of the three cases, so it is the one a design system has to be built for. Below are the two lines in Datastar that do the morphing.

datastar.js 1.0.4, the loop that goes through the attributes on every update

// r = the element in the page now, s = what the server sent,
// o = the names in data-preserve-attr. Just before, s is copied into r.
for (let {name: l} of Array.from(r.attributes))
  !s.hasAttribute(l) && !o.includes(l) && r.removeAttribute(l)

// If the attribute is there, but not in what the server sent,
// remove it. Unless the template has protected the name.
Variant:
EmailEnter a valid email address

The browser, the element r

To and from the server, the element s

The emergency exit is data-preserve-attr: the template lists everything the web component has set, and has to change in step with it, with no compiler to say so.

If a web component has added aria-describedby in the browser, it is gone at the next morph, and the screen reader loses the wiring without anything reporting it. React keeps the node on an ordinary re-render and leaves alone what it did not render, but replaces the node when the type or the key changes. The result is the same, only later. Therefore:

A web component never adds nodes to markup that someone else renders. Everything it writes there, it works out from the markup and from what the user does, so it can write the same again after every re-render.

Design system teamCannot count on anything a web component sets staying where it was put.

Requirement 2 of 5 · Markup must come from whoever renders it

Plain DOM, because a re-render does not reach into a shadow root

A shadow root can do more today than it could. The web component can join the form around it with ElementInternals, and a server can send the content as a declarative shadow root. Under the premise, four things still stand in the way.

  • A re-render does not reach inside. A declarative shadow root is created when the page is first parsed, not when a morph parses what the server sends, and neither Datastar nor idiomorph walks into one. Whoever renders can then neither write nor update what is in there.
  • Ids stop at the shadow root. A <label for> finds its field only in the same tree, so a label outside cannot point at a field inside. Reference Target, the proposal that would let it, has shipped in one engine.
  • A server without JavaScript has to copy the inside by hand. From Go, PHP or Kotlin, the template has to repeat each web component's inner markup, and change when it does.
  • The consumer's CSS stops at the shadow root. Inherited values, custom properties among them, and ::part() get through, and little else, which is at odds with requirement 5.

So the field is an <input> you write yourself, in plain DOM, and the web component wraps around it. The price is that a re-render reaches everything the web component has set. A shadow root would have protected it. Requirement 4 is about paying that price.

Design system teamGives up the one place where its own markup and state would have been safe from a re-render.

Sources, read 19 November 2026: MDN, ElementInternals (in all engines since March 2023) · web.dev, Declarative Shadow DOM (in all engines since August 2024; not created by innerHTML) · HTML Standard, the label element · caniuse, referenceTarget (Chrome 152 and Edge; behind a flag in Firefox and Safari) · MDN, Using shadow DOM (page CSS does not affect nodes inside) · datastar.js 1.0.4, read in the source.

Requirement 2 of 5 · Markup must come from whoever renders it

Two layers, and a component that sends a form value cannot create its own markup

Whoever renders writes the markup: classes, data-* and the wiring. The web component adds keyboard, focus and positioning, and the wiring where the markup lacks it. Whether it may create nodes of its own depends on what it is for.

CSS

Whoever renders creates everything, and no JavaScript runs.

<button class="lt-button"
  data-variant="secondary">
Frame

Whoever renders creates the nodes. The web component sets only attributes it can work out again.

<lt-field>
  <label for="…">…</label>
  <input id="…">
</lt-field>
Standalone

A toast or a connection bar. They create their content inside their own element, and send no form value.

toast.show("Saved")

A component that sends a form value, or has content that must come from whoever renders, cannot create its own markup. It is a frame.

Design system teamHas to place every new component in one of the three before it is written.

In LO-TEKThe documentation sorts the components the same way. The builder functions are in lt for TypeScript and in Lt for Kotlin, and run on a server without a DOM.

Requirement 3 of 5 · The wiring must have one source

Two paths to the same wiring, and one function behind both

What matters is whether there is a builder function for the language whoever renders is written in.

LO-TEKThere is a builder function: React, Astro, Node, Kotlin

import { lt } from "@lo-tek/interfaces/react"
const field = lt.field({ id: useId(), help: true })

<label {...field.label}>Email</label>
<input {...lt.input({ type: "email" })} {...field.control} />

LO-TEKThere is none: Go, PHP, Python, HTML by hand

  <label class="lt-label" for="email">Email</label>
  <input class="lt-input" id="email" type="email">
  <p class="lt-help-text">We never send spam</p>
</lt-field>

// The template writes id and for, as HTML requires.
// The web component adds the rest.

Both get the same wiring, because both call the same function:

computeFieldAttributes(...)
   ├── lt.field()   ← called where the markup is rendered
   └── <lt-field>   ← called in the browser, on elements already in the DOM

Rules of its own in the web component would be a second implementation, and that is the one that breaks first.

Design system teamHas to write the wiring as a pure function without a DOM, so that both a builder function and a web component can call it. Every language that cannot call it needs a copy, and a test that holds the copy to the source.

In LO-TEKKotlin cannot call the TypeScript function, so Lt.field() is written by hand. A test runs it against 277 combinations of options with the answer from TypeScript, and one difference stops the build.

Requirement 4 of 5

The web component must be able to write everything again

A re-render can tear away anything a web component has set. So the web component writes only what it can work out again, reads state that is in the markup from the markup, and remembers what it wrote itself and what the user did.

Ask of your own design systemIf a server morph strips the wiring your script wrote, or React replaces the node, is it written back without the template listing it, and is state such as aria-invalid read from the markup rather than kept as a copy?

  1. It reads, compares and remembers, and puts back what a re-render tears away
  2. State in the markup is read from the markup, and the web component knows what is its own

Requirement 4 of 5 · The web component must be able to write everything again

It reads, compares and remembers, and puts back what a re-render tears away

A re-render can remove what the web component set: DOM morphing strips the attribute, and React can replace the node. MutationObserver tells the web component, and it writes the attribute again. Three habits make that possible.

  • It reads before it writes. Ids and aria-describedby that were rendered are kept.
  • It compares before it writes, and writes nothing that is already there.
  • It remembers what it wrote, and on which node. Only that can it put back, and an id it created comes back the same.

LO-TEKThe helper the writes go through, simplified

function setAttr(el, name, value) {
  if (el.getAttribute(name) !== value) el.setAttribute(name, value)
}

It does not flicker: MutationObserver calls the web component in a microtask, before the browser paints again.

Design system teamHas to compare before every write. A web component that writes the same value again triggers its own MutationObserver, and the test run hangs instead of failing.

ConsumersWrite what HTML requires, such as id and for on a field, and nothing more: no aria-describedby and no list of what has to be preserved.

In LO-TEKSeven of the ten web components keep the memory in a WeakMap keyed by the node. <lt-field> never writes an id on the field: a morph matches nodes by their id and never keeps one whose id the new HTML lacks, so a field with an id the server did not send would be replaced at the next update, with focus and what the user typed.

Sources, read 19 November 2026: DOM Standard, mutation observers · HTML Standard, event loop.

Requirement 4 of 5 · The web component must be able to write everything again

State in the markup is read from the markup, and the web component knows what is its own

That a field is invalid is stated as aria-invalid on the field. A separate attribute on the web component's own element puts the state in two places, and sooner or later they disagree.

If the state is in the markup, the web component reads it from there, and keeps no copy of it.

Some attributes are written from both sides. aria-selected on a tab can come from whoever renders, and the web component sets it when the user picks another tab. To read it, the web component has to know who set the value that is there now.

Note the value the web component wrote, and on which node. If something else is there next time, someone else has touched it. Never decide it from what the web component believed last time.

What the user did is the one piece of state the markup never had, and the web component keeps it: which tab was chosen, which option was highlighted. A re-render tears it away, and by default the web component puts it back. Sometimes whoever renders should have the last word instead.

Design system teamHas to decide, component by component, whether a re-render or the user has the last word, and give the template a way to say which.

In LO-TEKTabs, suggestion, popover and dialog read server-controlled on their element. Then they no longer put back what the user did, and still do the wiring and the keyboard.

Requirement 5 of 5

The consumer's CSS must win

A consumer who has to write !important to move a button four pixels stops using the design system. So all component CSS is in a layer of its own, and an entirely ordinary rule written by the consumer beats it: a rule outside any layer wins over everything inside one.

Ask of your own design systemDoes a rule with one class selector in the consumer's CSS beat yours in every state, :disabled included, even when it is loaded first and without !important?

LO-TEKWithout the layer, your rule loses on specificity

.lt-button           (0,1,0)
.lt-button:disabled  (0,2,0)  ← the design system's wins

With the layer, your rule wins regardless

@layer lotek {
  .lt-button:disabled { … }
}
.lt-button { … }  ← unlayered, wins

Shape and size are read from a variable

padding: var(--lt-button-padding,
             var(--lt-spacing-2) var(--lt-spacing-4));

The default value follows the spacing scale, also when the consumer changes --lt-spacing-*. The variables are deliberately not registered with @property: a registered initial value becomes the value when the variable is not set, and then var() never reaches the fallback.

Design system teamHas to test the layer and the variables in a browser, not assume they work. Both have their own tests.

Recommendation 1 of 2 · Mistakes should be caught in every environment

A builder function knows its options, as a component does

The objection to leaving React is usually the developer experience: you lose components that know their own options. A builder function gives the same, because it is a plain TypeScript function: one object in, attributes out, and the editor knows both.

LO-TEKThe call, and what comes out

lt.button({ variant: "secondary" })
// { class: "lt-button", "data-variant": "secondary" }

lt.input({ type: "email", state: "invalid" })
// { class: "lt-input", type: "email",
//   "data-state": "invalid", "aria-invalid": "true" }

What every such function has to keep to

  • Always an object, never positional arguments.
  • A default the CSS already has gives no attribute.
  • The allowed values are in the type, so they show up in the editor.
  • One term means one thing in every function.

If you make a typo, for example variant: "secondry", you get a red squiggle in the editor before you save, wherever TypeScript sees the code: in JSX, in Astro and in JavaScript with type checking switched on.

Design system teamHas to keep the allowed values, the types and the CSS in step. A value that does nothing is worse than no value.

The web component should speak up when the markup does not fit together

HTML has no compiler. If a field is written without a label, nothing stops it, and the page looks entirely right.

The one who notices is the one who cannot see the screen. So the web component writes one line in the console, while the developer is still working on the code.

LO-TEKThe markup that was written

<lt-field>
  <input class="lt-input" id="date-of-birth">
</lt-field>

LO-TEKWhat the developer sees

lt-field: found no <label>, so the field
has no label and a screen reader
announces it without a name. …

A warning that raises false alarms gets ignored. Three choices make this one trustworthy:

  • It waits until the parser is done and two frames have passed. HTML arrives in pieces, so a moment without a label is normal.
  • The same text every time. A number in it, as in “Found 3 tabs, but 1 panel”, makes one warning into twenty.
  • It points at the real bug. The popover finds its button by looking up the panel's id. If the id is missing, the warning should say so, and not that the button is missing. Otherwise the developer looks in the wrong place.

Design system teamHas to keep valid markup free of warnings everywhere, or developers learn to ignore them.

In LO-TEKA check in CI reads the console on every page of the built documentation and fails if there is a warning in it.

Recommendation 2 of 2

A consumer should be able to take over the code

A design system never covers everything, and a consumer who needs something it has not thought of should be able to move on the same day. Instead of writing a wrapper around a component that falls short, the consumer copies the source code of that one component into the project.

Ask of your own design systemWhen tokens, variables and their own CSS are not enough, can a consumer copy one component's source into the app, upgrade the package, and still build?

The order to try: first tokens, then component variables, then the consumer's own CSS in a layer of its own. Only when none of these is enough does the consumer take over the component. The first three cost nothing to upgrade from.

LO-TEKThe source code of one component, into your project

Copied by hand, the component's imports would point at files the consumer does not have. The command rewrites them, so that ../shared.js becomes @lo-tek/interfaces/shared, and the rest of the design system still comes from the package and can be upgraded. The lookup is built from exports in the package.

Design system teamHas to make sure everything a component imports is in exports, or the copy points at something the consumer does not have.

The pitfalls

The bugs come where a design system meets React, a server without a DOM, or the code that runs before the web component is registered. Most were found in the three versions of the game, not in the unit tests.

  1. React 19 and web components
  2. The server and hydration

The pitfalls

React 19 and web components

If a web component has a property with the same name as an attribute, React 19 sets the property and not the attribute. That causes three bugs, and the first two give no error message:

  • A boolean attribute cannot be sent as an empty string. el.open = "" is falsy, and the setter removes the attribute again. Send true.
  • An option cannot borrow the name of a standard property. autofocus="false" becomes el.autofocus = "false", and a non-empty string is truthy. Put the option in data-*: no property has that name, so React sets it as an attribute.
  • A getter needs a setter. Without one, the assignment throws, and the attribute never arrives.

The spelling differs too. React wants className, htmlFor and tabIndex, and tabIndex as a number. A builder function that returns HTML names therefore needs a separate version for React.

Design system teamHas to test in a real React app.

In LO-TEKThe flags are sent as true, and the error summary's option is called data-autofocus.

The pitfalls

The server and hydration

An id that is generated automatically

The server and the browser each generate their own id, and React warns of a hydration mismatch in development. React does not promise to patch up attributes that differ, so the wiring between label and field can stay broken. Make id required in the type, and add a console message alongside for those the type does not reach.

A class that extends HTMLElement

class X extends HTMLElement is evaluated as soon as the module loads, and HTMLElement exists only in the browser. A server then cannot import anything from the package, not even a builder function. Extend a class that falls back to an empty class without a DOM.

Design system teamHas to import every module in an environment without a DOM, because no browser test can fail on this.

In LO-TEKHostElement is HTMLElement in the browser and an empty class without a DOM, and a script imports every entry in exports in Bun without a DOM.

Source, read 19 November 2026: react.dev, hydrateRoot (warns in development; no guarantee that attribute differences are patched up).

The pitfalls

Before the web component is registered

Until a web component is registered, it is a plain HTMLElement, with no methods and no behaviour.

  • Register on import, never in an effect. A useEffect runs only after React has put the elements in the DOM. If the app calls a method on the element before that, it gets “reportSuccess is not a function”.
  • An imperative call has to wait for registration. A helper that waits for customElements.whenDefined() for the element's own tag name makes the order irrelevant. It warns in the console if it takes too long.
  • The flicker before registration is solved in CSS. :not(:defined) applies until the web component is registered. With it, the stylesheet can show only the first panel, so whoever renders does not have to write hidden on the rest.

Design system teamHas to give every imperative call a way that works before registration: a helper that waits, or a property that is kept until the upgrade.

In LO-TEKdefineLt() registers the web components when the app calls it at start-up. The five exported helpers, such as showToast and reportFailure, wait by themselves and warn after three seconds, and a property set before registration, such as open on a popover or selected on tabs, is applied afterwards. Only a method called on the element itself fails until then, since it does not exist before the class is defined.

Checklist for your own design system

Answer each one by trying it on your own system, not by reading its documentation.

Requirements: without them it breaks

  1. With JavaScript switched off, does every component look as designed, and does the package install with no framework among its dependencies or peer dependencies?
  2. Apart from components that only show their own content, such as a toast, can a template that runs none of your code write every node, in plain DOM, with script adding attributes at most?
  3. Are the rules that connect a label, a field and its messages (id, for, aria-describedby) written once, with every way of rendering using them or a copy tested against them?
  4. If a server morph strips the wiring your script wrote, or React replaces the node, is it written back without the template listing it, and is state such as aria-invalid read from the markup rather than kept as a copy?
  5. Does a rule with one class selector in the consumer's CSS beat yours in every state, :disabled included, even when it is loaded first and without !important?

Recommendations: without them it is harder to use and to leave

  1. Are a developer and a coding agent told about an unknown class, an invalid value or a missing label while they write, also in templates and hand-written HTML, while valid markup gives no warning?
  2. When tokens, variables and their own CSS are not enough, can a consumer copy one component's source into the app, upgrade the package, and still build?

Pitfalls: where it breaks in practice

  • In a real React 19 app, does every option still work when React sets it as a property: booleans, names that are also standard properties, and getters without setters?
  • Does every module import on a server without a DOM, and are the ids the wiring needs the same on the server and in the browser?
  • Does an imperative call, such as showing a toast, work even when it runs before the custom element is defined, with no flicker before it?
