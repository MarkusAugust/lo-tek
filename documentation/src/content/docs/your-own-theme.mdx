LO-TEK has its own hues. If your organisation has others, you can write the cells by hand, but then keeping the contrast promises is up to you: every colour is part of several pairs, and every pair has to meet the requirement in both the light and the dark theme. `lotek check-theme` tells you if one breaks.

The generator takes your brand colours and builds the rest.


## Who decides what

The generator decides more than most theme tools do, and that is how it can promise the contrast.

- **You decide** the colours, by their hue and chroma, one for each family, and the font, the weights, the line heights, the three kinds of corners, and the border and the weight of the button.
- **The generator decides** how light every colour is, which families and roles there are, and with that the contrast, in the light theme and the dark. See [What the generator does](#what-the-generator-does).
- **Not in the recipe** are a scale for spacing or for type size, a light brand colour kept as the fill, and roles of your own. See [What the generator does not do](#what-the-generator-does-not-do).
- **The way out** is your own CSS. The theme is in a layer of its own, and CSS you write outside a layer beats it, so what the recipe does not have, you set there. See [The theme beats the defaults](#the-theme-beats-the-defaults) and [Customising](../customising/#when-the-variable-is-not-enough). The contrast of what you set yourself is yours to keep, and `lotek check-theme` checks it.

## Creating the theme

The generator is the same wherever you run it, and the recipe is what the ways share: a `lotek.theme.json`.

- **In the browser.** The [theme builder](/theme-builder/) shows LO-TEK's components with the theme as you set it, light and dark side by side, says what became of each colour, suggests [colours to go with your accent](#colours-to-go-with-the-accent), and gives you the recipe and the file. Nothing is installed, and what you enter is sent nowhere.
- **On the command line.** `npx @lo-tek/interfaces theme`, from flags or from the recipe. That is the rest of this section.
- **In a build step.** `buildTheme()` in TypeScript. See [Programmatic use](#programmatic-use).
- **From Kotlin and Gradle.** `Lotek.buildTheme()` and the `lotekTheme` task. See [The theme](../kotlin/#the-theme) on the Kotlin page.

Whichever you choose, you end up with one file, `theme.css`, and [Using it](#using-it) is the same.

```bash
npx @lo-tek/interfaces theme \
  --accent=#7c3aed \
  --danger=#b3261e \
  --success=#2b6940 \
  --warning=#8a5a00 \
  --neutral=#1a1a1a \
  --out=theme.css
```

Or with a file, which can live in the repository. Call it `lotek.theme.json`:

```json
{
  "accent": "#7c3aed",
  "danger": "#b3261e",
  "success": "#2b6940",
  "warning": "#8a5a00",
  "neutral": "#1a1a1a"
}
```

```bash
npx @lo-tek/interfaces theme lotek.theme.json --out=theme.css
```

All of them are optional. A family you leave out inherits LO-TEK's own hue.

| Family | Used for |
| --- | --- |
| `--accent` | Links, buttons and focus indication |
| `--danger` | Errors, deletion and rejection |
| `--success` | Completed and approved |
| `--warning` | Something that needs attention |
| `--neutral` | The page, body text and borders. Almost without hue |
| `--visited` | Visited links |
| `--brand1`, `--brand2`, `--brand3` | Surfaces, sections and categories. They mean nothing in themselves |

## Using it

The theme is one CSS file. Load it together with LO-TEK's own stylesheet, and that is all: the components take their colours, font and corners from it.

**With a bundler,** import it after `tokens.css`:

```css
@import "@lo-tek/interfaces/tokens.css";
@import "./theme.css";
```

**In plain HTML,** link it after LO-TEK's stylesheet:

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@lo-tek/interfaces@VERSION/dist/lotek.css">
<link rel="stylesheet" href="/theme.css">
```

**With Tailwind,** import it the same way, and put its layer in the layer order on the first line of your CSS:

```css
@layer theme, base, lotek, lotek-theme, components, utilities;
```

See [Layer order](../tailwind/#layer-order) for why the line has to be first.

The file overrides what the recipe mentions, and the rest still comes from `tokens.css`. It beats LO-TEK's defaults whichever of the two is loaded first, since it puts itself in a layer of its own; see [The theme beats the defaults](#the-theme-beats-the-defaults).

The theme covers both the light and the dark theme, and both the system setting and an explicit `data-theme`.

`color-scheme` decides how the browser draws its own surfaces: the dropdown of a `<select>`, scrollbars and the calendar panel in a date field. Without it they stay light on a dark page.

LO-TEK sets it wherever someone has chosen a theme: on `[data-theme="light"]`, on `[data-theme="dark"]` and on the three options of the [theme picker](../patterns/theme/). It is not set on bare `:root`, because the property is inherited, so a value there applies to the whole document. A child can opt out with `color-scheme: normal`, but that is a counter-rule the host never asked to have to write. If you want the browser's surfaces to follow the system on the whole page, write one line yourself:

```css
:root {
	color-scheme: light dark;
}
```

**If you use the theme picker, do not write that line.** Each of the three options sets `color-scheme` itself. If you write it anyway, outside a layer, the rule beats `@layer lotek`, and the browser's surfaces stay locked to the system while the user has chosen something else.

## What the generator does

**It fills the matrix.** Every family you give gets the nine roles, and every role gets its fixed lightness. If you give only some of the families, the rest inherit LO-TEK's own hues.

**The hue is yours, the lightness is the role's.** Give a light purple or a dark purple and you get the same purple family: the role decides how light each cell is, and that is what lets the contrast be guaranteed. The chroma is yours too, as far as sRGB can show it at the role's lightness: a muted brand colour gives a muted family, and a vivid one is lowered until it fits.

The computation happens in OKLCH, not in HSL. In HSL, lightness means something different for each hue: `hsl(60 100% 50%)` is bright yellow and `hsl(240 100% 50%)` is almost black, with the same numbers. In OKLCH, lightness is the same perceived lightness whatever the hue, so one lightness per role can apply to every colour.

**Contrast is guaranteed, not adjusted.** The lightnesses are computed against a sweep around the whole colour wheel, at the highest chroma sRGB can show for each hue. That is why the promises hold whatever brand colour you give, and there is no pass that adjusts the theme afterwards. There used to be one, and it ran every single time, because one step had been chosen too light.

Every theme is still checked against the promises before it is written out, and the run exits with an error if one breaks, rather than delivering a theme that only looks right. With an almost white or almost black brand colour that does not happen: the lightness is the role's, so such a colour just gives a grey family.

## What became of your colour

Since the lightness is the role's, the colour you gave is rarely one of the cells. A colour in the middle barely moves. A light one moves far: a yellow accent gives an olive fill. The run says so on standard error, for every colour you gave:

```
accent: #f7df1e gives the fill #7a6d00 in the light theme and #a19100 in the dark theme.
  In the light theme #f7df1e cannot be the fill as it is: against the page it would have a contrast of 1.35:1, and 3.1:1 is required; against a raised surface it would have a contrast of 1.06:1, and 3.1:1 is required; text on it would have a contrast of 1.32:1, and 4.6:1 is required.
  In the light theme the fill is less saturated than #f7df1e, with 61% of its chroma: a screen cannot show more at that lightness.
  In the dark theme the fill is less saturated than #f7df1e, with 74% of its chroma: a screen cannot show more at that lightness.
```

The first line is also written at the top of the generated file, so the file still says it later.

The second line is the reason: the promises about `fill` your colour would break if it were the fill itself, each said as what the fill is measured against. The theme does not break them. A colour that fits as the fill on a light page is too dark on a dark one, and the other way round, so every colour gets such a line for at least one of the themes.

## Colours to go with the accent

An organisation often has one colour, and a theme has nine families. The generator suggests five palettes for the ones you have not set:

| Palette | brand1, brand2 and brand3 |
| --- | --- |
| Near | The hues beside the accent on the colour wheel. |
| Opposite | The hues across the colour wheel from the accent. |
| Three ways | Three hues that share the colour wheel evenly with the accent. |
| One hue | The hue of the accent, in three saturations. |
| Quiet | The hues beside the accent, with less than half its saturation. |

Each also has a colour for `visited`, the accent muted, and for `neutral`, a grey with a faint cast of the accent. Those two are the same in all five. `danger`, `warning` and `success` are never suggested: red, yellow and green carry a meaning. A suggested brand colour whose hue lands near one of the three is moved away from it, and so is one that lands on the accent or on another suggestion. A palette is then less regular than its name, and its description says that hues were moved.

A suggestion is made at the lightness of the fill, so the colour you see is the fill the theme gets in the light theme, and not one the generator then moves. A family you have set yourself stands as it is.

In the [theme builder](/theme-builder/) each palette is a button under the accent, with its colours on it. Pressing one fills the families you have not set, pressing another swaps them, and "LO-TEK" takes the suggestions away again. From code, see [`suggestPalettes`](#programmatic-use).

## What the generator does not do

**It does not keep a light brand colour as the fill.** `fill` alone carries the state of a checked checkbox, a radio button, a switch and a progress bar. WCAG 1.4.11 requires 3:1 against the page there, and a yellow on white gives 1.35:1. A light brand colour therefore gives a darker family, and the colour itself belongs in the logo and in illustrations. If you write a light fill by hand, `lotek check-theme` reports the promises it breaks.

It does not pick colours for you. If you give a hue that is too close to another, for example an orange danger and a yellow warning, the two look alike in use even though both meet the contrast requirement. The colours have to be distinguishable from each other, and that is a judgement, not a calculation.

Nor does it touch the icons in `tokens.css`. They are drawn in neutral colours and work in both themes.

## Typography and shape

Colours are the hardest part to get right, which is why the generator started there. But two systems with the same hues still look different if the typeface and the corners differ. So the recipe can also say how things should look:

```json
{
  "accent": "#1362ae",
  "danger": "#a82e39",
  "success": "#316f2a",
  "warning": "#9f7509",
  "typography": {
    "fontFamily": "Helvetica, Arial, sans-serif",
    "weights": { "bold": 700 },
    "lineHeights": { "default": 1.666, "heading": 1.333, "article": 1.666 }
  },
  "shape": {
    "buttonRadius": "2.75rem",
    "fieldRadius": "0.25rem",
    "surfaceRadius": "0.5rem",
    "buttonBorderWidth": "3px",
    "buttonFontWeight": 700
  }
}
```

Six of the values also exist as flags: `--font`, `--button-radius`, `--field-radius`, `--surface-radius`, `--button-border` and `--button-weight`. The weights and line heights are set only from a file. A command line with eight typography numbers is unreadable, and typography is something you decide once and keep, which is exactly what a file in the repository is for.

A flag that does not exist stops the run rather than being ignored, so a typo is reported. The same goes for a key in the recipe file. The exception is `$schema`, which editors insert by themselves and which says nothing about the theme.

The keys are written in one schema, `@lo-tek/interfaces/theme.schema.json`, and the generator's tests hold it to the keys the generator knows. [LO-TEK for VS Code and the JetBrains plugin](../the-editor/) complete and check a file named `lotek.theme.json` against it, with nothing to set up. In another editor, name the schema in the file, with the path from the recipe to the package. For a recipe at the root of the project:

```json
{
  "$schema": "./node_modules/@lo-tek/interfaces/src/tokens/theme.schema.json",
  "accent": "#7c3aed"
}
```

The schema is stricter than the generator about how a colour is written. The generator also takes a colour without the `#`, and reads an empty one as not given. The schema asks for text with a `#`, so an editor marks the others.

These are the keys inside the two blocks, and a key that does not exist stops the run rather than being ignored:

| Key | What it sets |
| --- | --- |
| `typography.fontFamily` | the font stack, as a token and as a rule on `:root` |
| `typography.weights.regular` · `.medium` · `.semibold` · `.bold` | the four weights |
| `typography.lineHeights.default` | controls: button, input, table |
| `typography.lineHeights.heading` | headings |
| `typography.lineHeights.article` | body text and lists |
| `typography.lineHeights.compact` | small surfaces: help text, tooltip, card title |
| `shape.buttonRadius` | the button, pagination and the skip link |
| `shape.fieldRadius` | the input, the textarea and the select |
| `shape.surfaceRadius` | card, dialog, popover, alert, accordion, error summary, file upload, session timeout, the suggestion list, the toast, the tooltip and the panel of a term |
| `shape.buttonBorderWidth` | the border width of the button |
| `shape.buttonFontWeight` | the weight of the button text |

Everything here is optional. If you leave out both blocks, the theme is exactly what it was before: colours only.

### Without colours

If your organisation already uses LO-TEK's hues, it is the typeface and the corners that set it apart. Then you leave out the brand colours altogether, and get a theme that leaves the colours as they are:

```bash
npx @lo-tek/interfaces theme \
  --font="Helvetica, Arial, sans-serif" \
  --button-radius=2.75rem \
  --out=theme.css
```

A theme with no content at all throws. Give a colour, a font or a shape.

### Why three kinds of corners

A single shared number would be simpler and wrong. Another design system has fully round buttons and fields with almost square corners, and with one number the fields become capsules.

The checkbox, the badge, the tag, the toggle group, the avatar, the skeleton and the progress bar are left out. There the corner is not a style choice but the shape itself: a checkbox that turns round looks like a radio button, and a badge that turns square looks like a button.

### The theme beats the defaults

The generated file puts itself in its own layer, declared after the package's:

```css
@layer lotek, lotek-theme;
```

The declaration fixes the order regardless of when the stylesheets load, and that is not a detail: both Astro and TanStack Start put their bundled CSS right before `</head>`, that is, after a `<link>` you wrote yourself. If the theme were in the same layer as the package, it would lose to the defaults in those two. Both layers still come before unlayered CSS, so your own rules win as before.

If you use Tailwind, `lotek-theme` has to be in the layer order on the first line of your CSS, between `lotek` and `components`:

```css
@layer theme, base, lotek, lotek-theme, components, utilities;
```

A `@layer` statement only creates layers that do not exist yet. If `utilities` is already in the order when the theme declares its layer, `lotek-theme` ends up last, after `utilities`, and the theme beats your Tailwind classes. See [Layer order](../tailwind/#layer-order).

It applies both ways. If the theme is loaded as a `<link>` before the bundled CSS, the line in your CSS comes too late: the theme has already declared `lotek` and `lotek-theme`, so `base` ends up after them, and Preflight resets the components. Then the line has to be in a `<style>` first in `<head>`, before the theme. See [When LO-TEK and Tailwind are two stylesheets](../tailwind/#when-lo-tek-and-tailwind-are-two-stylesheets).

### The font is set as a rule

LO-TEK inherits the font on purpose, so a token alone would not change a single letter. If you give `fontFamily`, the generator therefore writes both the token and the rule that uses it:

```css
:root {
  font-family: var(--lt-font-family-base);
}
```

The rule is in `@layer lotek-theme`, like the rest of the theme, so your own unlayered CSS still beats it, and so does a layer declared after it, such as `utilities` in the order above.

## Programmatic use

If you need the theme somewhere other than the command line, for example in a build step:

```ts
import { buildTheme } from "@lo-tek/interfaces/theme"

const theme = buildTheme({
  accent: "#7c3aed",
  danger: "#b3261e",
  success: "#2b6940",
  warning: "#8a5a00",
})

theme.css        // finished CSS
theme.light      // the cells in the light theme, as an object
theme.dark       // the cells in the dark theme
theme.violations // promises that do not hold. Empty when the theme is fine
theme.brands     // what became of each colour you gave
```

Each row in `brands` has the `family`, the colour you gave as `given`, written `#rrggbb`, and `light` and `dark` with the `fill` it got, `chromaKept` as a share from 0 to 1, and `breaks`: the promises your colour would break as the fill itself, in the same form as `violations`. It also has what the core says about the colour, ready to show: `summary`, the first line `lotek theme` writes, and `reasons`, the sentences under it. Show them as they are rather than writing your own from the numbers.

If you build a form over the recipe, `checkRecipe` says everything that is wrong with it at once, where `buildTheme` refuses with one sentence:

```ts
import { checkRecipe } from "@lo-tek/interfaces/theme"

checkRecipe({ accent: "purple", shape: { buttonRadius: "1px (" }, colour: "#000" })
// [
//   { path: ["colour"], kind: "unknown", message: "Unknown key in the recipe: colour" },
//   { path: ["accent"], kind: "refused", message: "\"purple\" is not a valid hexadecimal colour. Colours are written as hexadecimal values, for example #7c3aed." },
//   { path: ["shape", "buttonRadius"], kind: "refused", message: "The value of buttonRadius has an unbalanced parenthesis, bracket or quote. …" }
// ]
```

Each problem has the `path` of its key as segments, since a key may have a dot in its name, the `kind`, and the `message` for a person. `unknown` is a key the recipe does not have and `refused` a value the core does not take. Two kinds are about the recipe as a whole and have an empty path: `empty`, when it gives nothing, and `notARecipe`, when it is not an object. Decide on `kind`, and show `message` as it is: its wording may change.

The list is empty exactly when `buildTheme` takes the recipe.

`recipeValues` is the other half of such a form: what the recipe gives, as the core reads it. Each key that has a value comes with its `path` and the value as `text`, and a key that is not given is not there. The text is the value as it is written, `#7C3AED` and not the `#7c3aed` that `brands` gives as `given`. Fill the fields from it rather than reading the recipe yourself, and the form cannot disagree with the generator about what counts as given: `0` is a value for a corner, and not a colour.

```ts
import { recipeValues } from "@lo-tek/interfaces/theme"

recipeValues({ accent: "#7c3aed", danger: null, shape: { fieldRadius: 0 } })
// [
//   { path: ["accent"], text: "#7c3aed" },
//   { path: ["shape", "fieldRadius"], text: "0" }
// ]
```

And `recipeBrands` says what became of each colour the generator takes, whatever else in the recipe is wrong: the rows `buildTheme` gives as `brands`. A form can show what a colour becomes while another field is still being written.

`suggestPalettes` gives the [colours to go with the accent](#colours-to-go-with-the-accent) of a recipe:

```ts
import { suggestPalettes } from "@lo-tek/interfaces/theme"

suggestPalettes({ accent: "#7c3aed", brand2: "#0d7a5f" })
// {
//   from: "#7c3aed",
//   palettes: [
//     {
//       name: "Near",
//       description: "The hues beside the accent on the colour wheel.",
//       colors: [
//         { family: "visited", color: "#7b53b2", kept: false },
//         { family: "brand1", color: "#a909bb", kept: false },
//         { family: "brand2", color: "#0d7a5f", kept: true },
//         { family: "brand3", color: "#c00077", kept: false },
//         { family: "neutral", color: "#6c6a74", kept: false }
//       ]
//     },
//     … Opposite, Three ways, One hue, Quiet
//   ]
// }
```

`from` is the accent the palettes are built on, LO-TEK's own when the recipe gives none. A row with `kept: true` is the recipe's own colour, and a family whose value the generator refuses has no row, so writing the rows with `kept: false` into the recipe writes over nothing. The answer is `null` when the recipe is not an object, and when its accent is not a colour.

The keys are the family names: `accent`, `visited`, `brand1` to `brand3`, `neutral`, `danger`, `warning` and `success`. They have the same names on the command line. A key that does not exist throws, with the same message as on the command line: the keys are checked by the core, so a typo is a typo wherever the theme is built.

The theme is computed by the core, written in Rust and compiled to WebAssembly, the same one `lotek theme` and LO-TEK for Kotlin use. `buildTheme` loads it from the package in Node, Bun and Deno. In the browser, for example in a theme picker, you load it yourself:

```ts
import { loadCore } from "@lo-tek/interfaces/diagnostics"
import wasmUrl from "@lo-tek/interfaces/core.wasm?url"
import contract from "@lo-tek/interfaces/color-contract.json?raw"

const core = loadCore(await WebAssembly.compileStreaming(fetch(wasmUrl)))
core.loadContract(contract)
const theme = core.buildTheme({ accent: "#7c3aed" })
```

The core has no colours in it. You give it the colour contract, that is, the lightness per role and the promises, with `loadContract`, from the file in the package. `?url` and `?raw` are Vite's way of getting the address of a file and its text. Without a build step, put `lotek-core.wasm` and `color-contract.json` from the package next to the page, and fetch them from there.

The core does the colour arithmetic. To ask whether a style sheet keeps the contract, give it to `checkTheme` from `@lo-tek/interfaces/theme-check`, which answers with the problems it found, or run `lotek check-theme` on the file, as [The check](#the-check) says. The lightness of each role and the contrast requirements are in `@lo-tek/interfaces/contract`, and LO-TEK's own colours in `@lo-tek/interfaces/matrix`.

## The check

The promises are run against twelve accent colours spread around the whole colour wheel, from bright red to almost black, each together with ten neutral colours from black and white to tinted grey, in both themes. If one cell is too light, the test fails with the pair that broke and how far off it was.

If you write the cells by hand rather than generating them, `lotek check-theme theme.css` is the same check on your own file.
